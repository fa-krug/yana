Yana Server

Yana isn't just a phone app. The app is a client, and the actual work happens on the Yana Server: a program you install and run yourself, on a home NAS, a Raspberry Pi, or any small VPS. It's free, open source, and there's nothing to sign up for. You install it, it runs on your own hardware, and it's yours.

What it actually does

Think of the server as the part of a feed reader that normally lives on someone else's infrastructure, except here it lives on yours. It goes out and checks your sources on a schedule, downloads new articles, strips out the ads and clutter, resizes images, and stores the finished result in its own database. When the app on your phone syncs, it isn't scraping the web itself, it's just asking your server "what's new," and your server already has the answer ready. That's also why the app works so well offline: everything it shows you was already fetched and processed before you opened it.

It ships as one process. No Redis, no queue workers, no separate database server to babysit, just Next.js, React, TypeScript, and a local SQLite file. If you can run a single Docker container or a single Node process, you can run Yana Server.

A unified API for very different sources

RSS, YouTube, Reddit, and podcasts don't have anything in common at the protocol level, and a handful of sites like heise, Tagesschau, or MacTechNews don't publish a usable feed at all. The server hides all of that behind one API: every source, however it's fetched under the hood, comes out the other side as the same kind of article, with the same fields, the same image handling, the same everything. The app never has to know or care what it's talking to. That's also what makes adding a new source mostly a server-side problem rather than something that needs a client update.

Aggregators

Each source type is handled by its own aggregator inside the server: one for generic RSS/Atom feeds, one for YouTube channels, one for Reddit communities, one for podcasts, and a set of hand-tuned scrapers for sites that are worth reading but never had a proper feed. New aggregators get added over time, usually because someone opened an issue asking for a source.

AI features

The server can generate short summaries of articles on request. Point it at an AI provider of your choice, OpenAI, Anthropic, Gemini, or a compatible endpoint, and the app can ask for a summary before you commit to reading the whole thing. This is entirely optional and off until you configure it: without a provider set up, the app just falls back to on-device Apple Intelligence, or skips summaries altogether.

Accounts

Sign-in uses passkeys, no passwords to leak. The first time the server starts it creates an administrator account, and from there that administrator invites and manages every other user. There's no open sign-up page, because there doesn't need to be.

Install with npm

npm install @sascha384/yana
yana

Then open http://localhost:3000.

Install with Docker

docker run -d \
  --name yana \
  -p 3000:3000 \
  -e BETTER_AUTH_SECRET="$(openssl rand -base64 32)" \
  -v yana-data:/app/data \
  -v yana-media:/app/media \
  sascha384/yana:latest

Then open http://localhost:3000.

Configuration

BETTER_AUTH_SECRET signs your session cookies, so generate a real one (the openssl rand -base64 32 above works fine) rather than leaving it blank. Beyond that, a handful of optional environment variables cover things like the database path, media storage path, the passkey relying-party ID, your public URL, timezone, and port; the README on GitHub lists all of them. Change the default admin account right after your first login.

Yana-Server

Yana ist nicht nur eine Handy-App. Die App ist ein Client, die eigentliche Arbeit übernimmt der Yana-Server: ein Programm, das selbst installiert und betrieben wird, auf einem NAS zu Hause, einem Raspberry Pi oder einem kleinen VPS. Kostenlos, Open Source, keine Anmeldung nötig. Installieren, auf eigener Hardware laufen lassen, fertig.

Was er wirklich tut

Der Server übernimmt genau den Teil eines Feed-Readers, der sonst irgendwo bei einem fremden Anbieter läuft, nur eben auf der eigenen Infrastruktur. Er prüft die Quellen nach Zeitplan, lädt neue Artikel herunter, entfernt Werbung und störenden Ballast, verkleinert Bilder und speichert das Ergebnis in einer eigenen Datenbank. Wenn die App auf dem Telefon synchronisiert, durchsucht sie nicht selbst das Web, sondern fragt lediglich den eigenen Server, was es Neues gibt, und der hat die Antwort bereits fertig. Genau deshalb funktioniert die App auch offline so gut: Alles, was angezeigt wird, wurde vorher schon abgerufen und aufbereitet.

Läuft als ein einziger Prozess. Kein Redis, keine separaten Worker, keine zusätzliche Datenbank zum Warten, nur Next.js, React, TypeScript und eine lokale SQLite-Datei. Wer einen einzelnen Docker-Container oder einen einzelnen Node-Prozess starten kann, kann auch den Yana-Server betreiben.

Eine einheitliche API für sehr unterschiedliche Quellen

RSS, YouTube, Reddit und Podcasts haben auf Protokollebene wenig gemeinsam, und Seiten wie heise, Tagesschau oder MacTechNews bieten gar keinen brauchbaren Feed an. Der Server versteckt das alles hinter einer einzigen API: Jede Quelle kommt am Ende als derselbe Artikel-Typ heraus, mit denselben Feldern, derselben Bildbehandlung, egal wie sie im Hintergrund geholt wurde. Die App muss nie wissen, womit sie eigentlich spricht. Das macht eine neue Quelle meist zu einer reinen Server-Aufgabe, ohne dass ein App-Update nötig wäre.

Aggregatoren

Jeder Quellentyp wird im Server von einem eigenen Aggregator behandelt: einer für generische RSS-/Atom-Feeds, einer für YouTube-Kanäle, einer für Reddit-Communities, einer für Podcasts, dazu eine Reihe handgepflegter Scraper für Seiten, die lesenswert sind, aber nie einen ordentlichen Feed hatten. Neue Aggregatoren kommen mit der Zeit dazu, meist weil jemand ein Issue mit einer Quelle vorgeschlagen hat.

KI-Funktionen

Der Server kann auf Anfrage kurze Zusammenfassungen von Artikeln erzeugen. Dazu wird ein KI-Anbieter der eigenen Wahl eingerichtet, OpenAI, Anthropic, Gemini oder ein kompatibler Endpunkt, und die App kann dann vor dem eigentlichen Lesen eine Zusammenfassung anfragen. Das ist vollständig optional und standardmäßig aus: Ohne eingerichteten Anbieter greift die App auf Apple Intelligence auf dem Gerät zurück oder lässt Zusammenfassungen einfach weg.

Konten

Die Anmeldung erfolgt per Passkey, keine Passwörter, die verloren gehen können. Beim ersten Start legt der Server ein Administratorkonto an, und von dort aus lädt diese Person alle weiteren Nutzer ein und verwaltet sie. Eine offene Registrierungsseite gibt es nicht, weil sie nicht gebraucht wird.

Konfiguration

BETTER_AUTH_SECRET signiert die Sitzungs-Cookies, deshalb einen echten Wert erzeugen (der obige Befehl mit openssl rand -base64 32 reicht dafür) statt ihn leer zu lassen. Daneben gibt es einige optionale Umgebungsvariablen für Dinge wie den Datenbankpfad, den Medienpfad, die Passkey-Relying-Party-ID, die eigene öffentliche URL, Zeitzone und Port; die vollständige Liste steht im README auf GitHub. Das Standard-Administratorkonto direkt nach der ersten Anmeldung ändern.
